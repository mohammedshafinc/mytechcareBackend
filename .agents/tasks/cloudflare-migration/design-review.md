# Cloudflare Migration Technical Design Review

## Findings

1. **MEDIUM — The refresh-cookie design is configurable, but browser authentication is not feasible-guaranteed for the stated Vercel + `workers.dev` topology.** In **Worker lifecycle and Wrangler**, **Authentication, cookies, and bootstrap**, and **Testing and deployment documentation**, staging uses a host-only cookie on `*.workers.dev` and production allows a Vercel hostname while setting `Domain=.mtechcare.com`. Requests from a `*.vercel.app` page to either `*.workers.dev` or `api.mtechcare.com` are cross-site; modern browser third-party-cookie blocking can prevent the refresh cookie from being stored or sent even with `SameSite=None; Secure`. CORS correctness does not override browser cookie policy, and Worker HTTP tests cannot prove this browser behavior. This can leave initial login working while refresh silently fails. **Concrete fix:** lock a same-site production topology as a release requirement: map the Vercel frontend to a sibling custom hostname such as `app.mtechcare.com`, map the Worker to `api.mtechcare.com`, leave `COOKIE_DOMAIN` empty so the refresh cookie is host-only to the API, and allow exactly `https://app.mtechcare.com`. Treat `workers.dev` as curl/API validation unless an actual supported browser passes an explicit login → reload → refresh → logout test. Add that browser smoke test and state that cutover is blocked if it fails. If the owner will not configure a same-site frontend hostname, replace cookie refresh with a separately reviewed token/CSRF design rather than assuming third-party cookies work.

2. **MEDIUM — Abuse controls for the public service-request endpoints are asserted but not specified or testable.** The normative **Password feasibility and login abuse control** amendment says “Public service-request abuse controls use a separate bucket,” but gives no key derivation, thresholds, window, `Retry-After`, cleanup rule, or even whether it covers both public `POST /api/service-request` (D1 writes and notification trigger) and `GET /api/service-request/by-mobile` (PII/rows-read enumeration). The `auth_rate_limits.window_seconds` constraint permits only 300 or 900 seconds, and the documented key formula lacks an operation discriminator; a coder could accidentally share a bucket with login/bootstrap or protect only create. This matters to the strict free-quota goal and to the existing public lookup exposure. **Concrete fix:** choose exact rules, for example:
   ```text
   HMAC inputs include an operation: public-create:ip:<ip> and public-lookup:ip:<ip>.
   POST /api/service-request: 10 attempts/IP/15 minutes.
   GET /api/service-request/by-mobile: 30 attempts/IP/5 minutes.
   Rate checks occur before any domain read/write; over-limit returns the generic 429 body
   plus Retry-After and performs no service-request query/insert.
   Missing/invalid CF-Connecting-IP uses a fixed operation-specific unknown bucket.
   ```
   Confirm the chosen 300/900-second windows fit the table check, define bounded expiry deletion, and add concurrent-threshold, bucket-separation, no-D1-domain-operation-after-429, and quota-budget tests. If intentionally preserving unlimited public lookup is required, say so explicitly and remove the unsupported “public abuse controls” claim, but that choice should be rejected for the $0 design.

3. **MEDIUM — A global notification cursor can permanently skip an event when an admin’s effective permissions change.** In **Persistent notification polling**, visibility is evaluated from current effective permission while one global integer `after/nextCursor` spans both event types. Example: an admin can see `new-request` IDs 10 and 12 but cannot see `expiry-alerts` ID 11; polling advances its cursor to 12. If STAFF permission is later granted, ID 11 is now authorized but can never be returned after cursor 12. Thus the current model does not fully establish the claimed “resume by cursor without loss” behavior for an application whose admin permissions are mutable. The three-admin tests only promise interleaved read state, not grant/revoke behavior. **Concrete fix:** choose and test one semantic:
   - **Recommended:** entitlement is fixed at creation. Add `notification_recipients(notification_id, admin_user_id, read_at NULL, PRIMARY KEY(...))`, atomically insert eligible active admins when publishing, query each admin’s recipient rows by notification ID, and create recipients for a newly bootstrapped/admin account only for future notifications. Permission changes do not retroactively add old events.
   - **Alternative:** retain dynamic visibility but keep a separate persisted cursor per event type/permission stream and require typed polling; never advance one stream because another type was returned.
   In either case, specify behavior for permission grant, revoke, account creation/deletion, and regrant, and test three admins with mixed event types around a permission change.

4. **NIT — Canonical date/timestamp storage is named but not given an implementable canonical form or SQLite check.** In **Fresh D1 schema contract**, `DATE` means a “real” Gregorian date and `TS` means canonical UTC RFC 3339, but RFC 3339 has multiple equivalent spellings and SQLite’s date functions can normalize or accept edge values differently by runtime version. This can produce inconsistent storage and invoice hash/UBL bytes. **Concrete fix:** lock `DATE` to exactly ten ASCII bytes `YYYY-MM-DD` validated by shared leap-year/calendar code before binding, and `TS` to exactly JavaScript `Date.prototype.toISOString()` output (`YYYY-MM-DDTHH:mm:ss.sssZ`, 24 ASCII bytes). Put the exact SQL shape/length checks in the migration and make service validation own Gregorian validity; add leap-day, February 30, offset normalization, missing-millisecond, and round-trip tests.

5. **NIT — The unknown-account dummy password record could be implemented as a source-controlled hash contrary to repository hygiene.** The **Password feasibility and login abuse control** amendment calls it a “process-constant syntactically valid dummy v1 hash” but does not say how it is produced. A literal encoded hash would conflict with the design’s broad no-password/hash-in-source rule and may trigger secret scanners, even though it authenticates no account. **Concrete fix:** state that isolate initialization generates random 16-byte salt and 32-byte comparison bytes with Web Crypto and constructs the in-memory v1 record; no literal encoded hash/password is committed or logged. Unknown-account verification derives from the submitted password using that salt and full-compares with the random bytes. Test format validity and equivalent derivation work without snapshotting the generated value.

## Verified Assumptions

- The design’s table inventory covers all 23 TypeORM entities identified in source/audit: `users`, `admin_users`, `stores`, `staff`, `service_requests`, `repair_items`, `bills`, `b2c_enquiries`, `corporate_enquiries`, `enquiry_followups`, `modules`, `submodules`, `user_modules`, `user_submodules`, `invoices`, `invoice_items`, `job_sheets`, `job_sheet_items`, `quotations`, `quotation_items`, `vehicles`, `vehicle_expenses`, and `rental_vehicles`. The D1 contract also includes `role_modules` and the required operational tables.
- `role_modules` is required by executable source: `AuthService.getModulesForRole()` runs `SELECT module_code FROM role_modules WHERE role = $1`. There is no checked-in entity or authoritative seed for it. The design correctly defines a fresh table, seeds no guessed role mappings, and fails closed for non-super-admin role fallback.
- The checked-in SQL migration surface consists of `migrations/add_staff_extended_fields.sql` and its rollback. The D1 staff contract contains the extended columns, and the normative amendment explicitly translates all nine source indexes (`employee_status`, email, primary mobile, visa, insurance, iqama, passport, driving-license expiry, and join date).
- Current visible-number generation is race-prone: invoice/quotation/job-sheet use `MAX(id)+1`, service requests derive a reference after insertion, and store/staff preview scans codes. The revised design uses atomic `number_counters` allocation, Riyadh-year scope for service requests, exact store/staff formats, and no table scan or `MAX(id)+1` in the target path.
- Current invoice/quotation/job-sheet parent and item writes use TypeORM transactions, and follow-up changes use a transaction with parent closure. The revised lookup-CTE child insert is feasible in a prebuilt D1 batch: it does not require piping `RETURNING id` between statements, and a missing parent becomes a `NOT NULL` failure that rolls back the batch.
- Password v1 is not weakened: PBKDF2-HMAC-SHA-256, 600,000 iterations, 16 random salt bytes, and 32 derived bytes are fixed and versioned. Workers Web Crypto exposes the required PBKDF2/HMAC/SHA-256 primitives. The first-milestone deployed benchmark correctly remains a release gate rather than lowering security parameters.
- `0 5 * * *` is 08:00 in Asia/Riyadh because Riyadh is UTC+3 without daylight-saving transitions. The revised scheduled-run contract has one Riyadh-date key, token ownership, an expiring lease, stale-owner rejection, failed/expired manual retry, completed-run rejection, and a unique `expiry-alerts:<date>` event. Zero alerts complete without publishing, matching the current service.
- The notification read state is independent per admin because receipt keys include both notification and admin IDs. Under unchanged permissions, ordered IDs and per-admin receipts support disconnect/resume and prevent one admin from marking another admin’s notification read. Finding 3 covers the remaining mutable-permission cursor case.
- CORS and cookie attributes are runtime-configurable: origins are exact allow-list matches, wildcard credentialed CORS is rejected, staging omits `Domain`, and set/clear attributes are shared. No runtime `.mtechcare.com` constant is required. Finding 1 concerns browser third-party-cookie feasibility, not the configurability requirement.
- No real Cloudflare account ID, D1 database ID, JWT/rate-limit/bootstrap secret, default-admin password, or credential value is specified for source control. Tracked Wrangler configuration is placeholder-only; ignored environment configs hold real IDs, and CI substitutes a dummy UUID.
- `AppModule` registers auth/admin, service requests, documents/bills/repair alias, all enquiry modules, reports, module definitions, stores/staff, organization/vehicles, notifications, TypeORM, and Nest Schedule. The route inventory covers these reachable HTTP families, and the target has one Worker entry while removing Nest bootstrap, TypeORM, PostgreSQL SQL, Socket.IO, and in-process scheduling from the deployed graph.

## Unverified/Wrong Assumptions

- **Unverified:** refresh cookies work from the actual Vercel frontend to `workers.dev` or `api.mtechcare.com`. Exact CORS and `SameSite=None` are insufficient when the browser blocks third-party cookies; see finding 1.
- **Wrong/incomplete:** saying public service-request controls use a separate bucket is enough to implement them. No operation key, thresholds, coverage, or failure contract is defined; see finding 2.
- **Wrong/incomplete:** a single filtered global notification cursor guarantees no lost authorized event across permission changes. Mixed event types can advance beyond an event that later becomes visible; see finding 3.
- **Unverified:** PBKDF2 at 600,000 iterations, XML/hash work, and the heaviest report SQL fit Workers Free CPU in the deployed runtime. The design correctly makes the password benchmark a mandatory pre-migration release gate; comparable staging measurements still must be recorded for document/report paths before cutover.
- **Unverified:** complete UBL UTF-8 bytes, TLV/Base64, and invoice-chain fixtures remain byte-identical after extraction. The current source’s whitespace, escaping, fallbacks, payload delimiters, and first-invoice hash behavior were inspected, but only the planned Worker-runtime golden fixtures can verify parity.
- **Unverified:** the exact SQLite/D1 runtime rejects all impossible date and noncanonical timestamp values using the eventual migration checks. The current prose does not yet define those checks; see finding 4.
- **Unavailable and intentionally not required:** the suspended RDS schema and data. The user explicitly chose a fresh database, so the source entities, both checked-in staff SQL files, executable raw SQL, controllers/services, and module registration are the available schema/behavior sources.

## Verdict

**CHANGES_REQUESTED** — 0 HIGH, 3 MEDIUM, 2 NIT findings.

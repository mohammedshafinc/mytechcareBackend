# Amended Cloudflare Migration Design Review

## Findings

No HIGH, MEDIUM, or NIT findings. The five previously open findings are fully resolved with concrete implementation rules and testable acceptance criteria.

## Verified Assumptions

1. **Same-site refresh-cookie topology is concrete and feasible.** The design locks production to an exact configured Vercel custom hostname beneath `mtechcare.com` (documented as `https://app.mtechcare.com`) calling `https://api.mtechcare.com`, with a host-only `refreshToken` cookie, `COOKIE_DOMAIN=''`, no `Domain` attribute, production `SameSite=Lax`, and exact credentialed CORS origins. It limits `workers.dev` to API/curl validation unless the browser sequence passes, blocks cutover without recorded login → full reload → refresh → logout evidence on the final hostnames, and explicitly makes `vercel.app`-only cookie refresh unsupported pending a separate non-cookie refresh/CSRF design. This intentionally replaces the existing `src/auth/auth.controller.ts` behavior, which emits `Domain=.mtechcare.com` and production `SameSite=None`; no claim is made that the old cookie helper already has the required behavior.

2. **Public service-request rate limiting is operation-specific and precedes domain access.** Source confirms both public operations exist in `src/service-request/service-request-public.controller.ts`, and `src/service-request/service-request.service.ts` shows that create performs request writes/numbering/notification work while lookup performs a mobile query. The amended design defines HMAC inputs `public-create:ip:<canonical-ip>` and `public-lookup:ip:<canonical-ip>`, limits of 10/900 seconds and 30/300 seconds, separate fixed unknown-IP buckets, an atomic concurrent upsert/check, generic `429`, integer `Retry-After: max(1, ceil(windowEnd-now))`, and ordering before every service-request repository query/write/counter/notification operation. The only D1 work permitted for a rejected request is rate-limit bookkeeping. Both windows satisfy `CHECK(window_seconds IN (300,900))`; cleanup is one statement capped at 500 expired rows. Concurrency, operation/unknown/auth/bootstrap separation, rollover, response, cleanup, and no-domain-D1-after-rejection tests are all explicit.

3. **Notification publication and permission lifecycle semantics are complete.** Source confirms the legacy event names are `new-request` in `src/admin/admin.gateway.ts` and `expiry-alerts` in `src/notification/notification.service.ts`. Source RBAC constants confirm `CLIENTS/SERVICE_REQUESTS` and `ORGANIZATION/STAFF` are valid module/submodule pairs, and `src/auth/auth.service.ts` confirms the explicit-user-then-role module fallback that the trigger must reproduce. The design adds `notification_recipients(notification_id, admin_user_id, read_at)` with cascade keys and polling indexes; notification creation and eligible-active-admin recipient insertion occur atomically, and polling/read/status operations begin from caller recipient rows ordered by notification ID. New accounts and first grants are future-only with no backfill; revoke/deactivate/block suppress fetch/read without deleting assignments; regrant/reactivation restores only previously assigned rows whose notifications still exist and preserves read state. The suppressed-row cursor barrier prevents later mixed-type IDs from skipping a restorable assignment. Three-admin mixed-event tests cover creation, grant, revoke, regrant, deactivation/reactivation, deletion, ordering, read state, no backfill, suppression, and restoration.

4. **DATE and TS contracts are implementable at both schema and service layers.** The design defines DATE as ten ASCII bytes shaped `YYYY-MM-DD` and TS as the 24-byte UTC `YYYY-MM-DDTHH:mm:ss.sssZ` output of `Date.prototype.toISOString()`. It provides concrete `length(CAST(column AS BLOB))` and `GLOB` checks, including nullable handling; shared validation owns Gregorian leap-year/calendar, clock, and offset semantics; and persistence mappers reassert canonical output. Tests explicitly cover valid and invalid leap dates, impossible dates, valid offset normalization, missing milliseconds normalized to `.000Z`, direct noncanonical persistence rejection, and byte-for-byte round trips. Source `src/service-request/dto/create-service-request.dto.ts` currently accepts a general ISO date string and the service constructs `Date`; the design does not incorrectly claim that this existing validation already enforces the new canonical persistence contract.

5. **Unknown-account password work and dummy-record hygiene are fully specified.** The design requires module/isolate initialization to make independent Web Crypto `getRandomValues` calls for a 16-byte salt and 32-byte comparison value, construct a syntactically valid v1 record only in memory, and never commit, log, return, fixture-store, serialize, or snapshot generated bytes. A validly shaped unknown-account request performs the same configured 600,000-iteration PBKDF2 derivation and all 32 XOR comparison steps as a known-account verification before returning the same generic `401`. Tests spy only on requested lengths, record shape, derivation count, and comparison-step count, without asserting generated values. This is a deliberate replacement for the current bcrypt path in `src/auth/auth.service.ts`, not an unsupported claim about an existing helper.

## Unverified/Wrong Assumptions

- **Unverified until deployment:** actual browser cookie storage/sending on the final custom hostnames. The design correctly treats dated real-browser evidence as a mandatory cutover gate rather than assuming HTTP/CORS tests prove browser behavior.
- **Unverified until implementation tests:** D1 concurrent rate acquisition, trigger recipient parity with the service RBAC evaluator, exact schema rejection behavior in the Workers D1 runtime, and unknown/known PBKDF2 work-equivalence. Each has a concrete Worker/D1 integration or unit-test oracle in the amended design.
- **Wrong assumptions found in the five scoped resolutions:** none.

Finding counts: **0 HIGH, 0 MEDIUM, 0 NIT**.
